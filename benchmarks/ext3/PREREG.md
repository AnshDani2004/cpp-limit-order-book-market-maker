# Extension 3(a) pre-registration: this repo's order book vs Liquibook on one identical stream

Status: FROZEN at the commit whose message starts `FREEZE ext3a`. Written before any timed run.
Everything below (stream, mapping, flags, harness, schedule, load rule, decision rule, summary
script) is fixed by that commit. Any later change is a deviation and must be listed in RESULTS.md.

## 1. Question

On the same Apple M3, with the same compiler, flags, harness and timer, replaying the same
1,000,000-event synthetic stream, is this repo's matching engine (map book, the configuration
quoted on the resume) faster than, slower than, or not clearly different from Liquibook, a named
open-source C++ limit order book? Measured: events/s over the whole measured loop, and p50 and
p99 per-event latency.

This is a single-thread, single-instrument, in-memory throughput comparison on a synthetic stream.
It says nothing about other hardware, real feeds, networking, or multi-threaded use.

## 3. The stream (identical for both engines)

Generator: `benchmarks/ext3/gen_stream.cpp`, seed 42, `std::mt19937_64`. It re-implements the
repo's hand-chosen `FlowGenerator` (`benchmarks/orderbook_benchmark.cpp`): 20,000 warm-up limit
adds, then 1,000,000 measured events drawn with weights limit 60 / market 10 / cancel 20 / modify
10; sizes uniform 1 to 100; limit prices reference +/- U{5..200} ticks; the reference does a +/-1
random walk held within 100,000 +/- 250. Cancels and modifies always target a live order (the
generator tracks liveness with the repo's own engine, as the original does). Two deliberate changes
from the repo's benchmark stream, both because a feature exists in only one engine:

1. **No owner IDs.** Every order has an empty `owner_id`. Self-trade prevention exists only in this
   repo's engine (Liquibook has none). With an empty owner the repo's `would_self_trade` returns at
   its first line, so no STP work is done.
2. **Every modify is a cancel/replace to a new price.** The new price is drawn by the same passive
   rule and redrawn until it differs from the current price; the new size is U{1..100}. Reason:
   the repo keeps time priority on a same-price size reduction (`modify_order` -> `reduce_order`),
   but Liquibook's `replace()` always erases the order and re-inserts it at the back of its price
   (`order_book.h`, `replace`: `market.erase(pos); matched = add_order(order, price);`). A
   price-changing replace loses priority and can re-match in both engines, so it is the common
   subset. The repo's same-price reductions (about half of its benchmark modifies) are excluded.

Stream file: `benchmarks/ext3/build/stream_seed42.csv` (not committed; regenerated by
`build/gen_stream`), columns `phase,action,id,side,price,qty,ts`, 1,020,000 rows.
SHA-256 `e1e9535a678b5c581ebb461b5d78a5307674203258e8ea24e98f93f30a8c3394` (checked by
`run_timed.sh` before any timed run). Measured-phase mix (printed by the generator): 599,678 limit
adds, 100,557 market orders, 199,517 cancels, 100,248 cancel/replaces.

Each harness process parses the CSV into a `std::vector<Event>` (action, side, id, price, qty, ts)
before anything is timed; both engines read the same in-memory structs.

### Event mapping

| stream event | this repo | Liquibook |
|---|---|---|
| limit add | `submit_order(Order::limit(id, "", side, price, qty, ts))` | adapter creates the order object, `live[id] = ptr`, `book.add(ptr)` |
| market order (unfilled rest cancelled) | `submit_order(Order::market(id, "", side, qty, ts))` (the repo cancels any unfilled remainder) | order object with price 0 (`MARKET_ORDER_PRICE`), `book.add(ptr, oc_immediate_or_cancel)` |
| cancel | `cancel_order(id, ts)` | `ptr = live[id]`, `book.cancel(ptr)` |
| cancel/replace (new price, new size) | `modify_order(id, new_price, new_qty, ts)` (cancel, then re-add at the back with the new size; may trade) | `book.replace(ptr, new_qty - open_qty, new_price)` (erase, re-add at the back; may trade); the listener's `on_replace` updates the order object's price and open quantity |

Trades are at the resting order's price in both engines.

## 4. Semantic-equivalence check (precondition; the comparison is invalid without it)

`build/ext3_harness check <stream>` replays warm-up plus measured events into every configuration,
untimed, and compares: measured trade count, measured traded volume, rejects (must be 0), an FNV-1a
hash of the full trade sequence (event index, maker id, taker id, price, quantity, in order), and
the final book (best bid and ask with their sizes, number of levels, orders and total size per side,
and an FNV-1a hash of every level's price, total size and order count). PASS requires every value
to equal the repo map book's.

Result before the freeze (run once, untimed; the shell's `time` wrapper was used only to see how
long the check took and is not a measurement):

| engine | measured trades | measured volume | rejects | trade-sequence hash | best bid (size) | best ask (size) | levels bid/ask | orders bid/ask | size bid/ask | final-book hash |
|---|---|---|---|---|---|---|---|---|---|---|
| map, flat, lb_new, lb_pool, lb_shared (all identical) | 372,120 | 9,486,560 | 0 | faae67780bb4e8f2 | 100142 (57) | 100153 (16148) | 575 / 298 | 72,627 / 72,110 | 3,667,041 / 3,645,589 | 634497979a84c9d0 |

`EQUIVALENCE=PASS` for both binaries (`ext3_harness` and `ext3_harness_unity`).

Negative control (shows the check can fail): the same generator with
`--negative-control-original-modify` keeps the repo's original modify rule (50% same-price size
reductions; stream SHA-256 `b6a791b6359da1b838aa88fe73a578252fd8c7511d8af7fc56fcc7ba3df9ee95`).
Result: `EQUIVALENCE=FAIL`. map and flat agree with each other (365,276 trades, volume 9,206,720,
0 rejects); all three Liquibook configs give 365,229 trades, volume 9,207,013, 20 rejects (cancels
or replaces addressed to ids the Liquibook adapter no longer holds, i.e. orders already filled
there, consistent with their reductions having sent them to the back of the queue) and a different final book. So the check detects the priority difference, and
the change in section 3 item 2 is necessary, not cosmetic. This stream is not timed.

Saved outputs: `results/equivalence/check_ext3_harness.txt`, `check_ext3_harness_unity.txt`,
`negative_control_original_modify_check.txt`, `stream_sha256.txt`.

Every timed run must also reproduce 372,120 trades, 9,486,560 volume and 0 rejects; a run that does
not is invalid (reported, not replaced).

## 5. Build (identical for both engines)

`benchmarks/ext3/build.sh`: Apple clang 21.0.0 (clang-2100.1.1.101), flags
`-O3 -DNDEBUG -std=c++20 -arch arm64 -Wall -Wextra` for every translation unit (repo engine
sources, generator, harness, Liquibook headers). No LTO, no PGO, no `-march`/`-mcpu` tuning for
either. Liquibook headers are included with `-isystem` (this only silences its warnings).

Two binaries from the same harness source:

* `ext3_harness`: the repo engine is linked as a separate static library (as the repo ships it).
  Liquibook is header-only, so it is always compiled inside the harness translation unit and can be
  fully inlined; the repo's non-template functions (`OrderBook::add_resting_order`, etc.) cannot be
  inlined across the library boundary without LTO. This asymmetry is how each project is designed
  to be consumed.
* `ext3_harness_unity` (`-DEXT3_UNITY`): the repo engine's four `.cpp` files are included into the
  harness translation unit, removing that asymmetry. Used only for the secondary `map_unity` config.

## 6. Harness and timer (identical for both engines)

`benchmarks/ext3/ext3_harness.cpp`, the same loop as `replay_flow` in
`benchmarks/orderbook_benchmark.cpp`: fresh engine in a fresh process; apply the 20,000 warm-up
events untimed; reserve the latency vector; then for each of the 1,000,000 measured events
`t0 = steady_clock::now(); adapter.apply(event); t1 = steady_clock::now();` and push `t1 - t0`.
Throughput = 1,000,000 / wall time of the whole measured loop (so it includes two clock reads and a
`push_back` per event, the same for every engine). Percentiles: sorted samples, index
floor(p * (n - 1)) (same as the repo). On this machine `steady_clock` advances in about 41.7 ns
ticks (audit timer probe), so p50 values are a few ticks and coarse; throughput is the primary metric.

Work inside the timed window, per event:

* both: building the engine's input from the `Event` struct; counting trades and summing volume
  (`++trades; volume += qty`). The trade-sequence hash is compiled out of timed runs.
* this repo: its full public API path: `ExecutionResult` returned by value (contains a
  `std::vector<Trade>`, heap-allocated when an order trades, and a `std::optional<Order>` copy;
  `Order` is 88 bytes with a `std::string`); duplicate-id check against an ever-growing
  `unordered_set` of seen ids (insert per new order); `contains` check; an empty-owner STP early
  return; `snapshot_order` copies on cancel and modify; a `std::list` node per resting order; a
  `std::map` node per new price level; an `unordered_map` location insert/erase.
* Liquibook: an `OrderTracker` copy in a `std::multimap` node per resting order (one tree node per
  order, keyed by price); a `Callback` pushed to a vector per accept, fill, cancel, replace and a
  `book_update` per call, then a dispatch loop (try/catch, the book's own virtual `on_*` no-ops,
  then the listener's virtual methods); `set_market_price` plus an empty stop-order scan per fill;
  cancel and replace locate the order by `multimap::find(price)` then a linear scan along that
  price's orders; replace always erases and re-inserts.
* Liquibook adapter (needed because the stream addresses orders by id and Liquibook by pointer):
  an `std::unordered_map<id, OrderPtr>` (the container type the repo uses internally), insert on
  add, erase on cancel or full fill; listener `on_fill` decrements both orders' open quantity and
  queues fully filled resting ids for removal after the call; `on_replace` updates price and open
  quantity. Order-object ownership differs by configuration (section 7).

## 7. Configurations and schedule

| config | role | what it is |
|---|---|---|
| `map` | PRIMARY (A) | repo engine, `std::map` book, `ext3_harness` |
| `lb_new` | PRIMARY (B) | Liquibook, `OrderBook<LbOrder*>`; order object `new`-ed inside the timed event and `delete`d inside the timed event when it leaves the book (closest to the repo, which allocates a list node per resting order) |
| `flat` | secondary | repo engine, `FlatOrderBook(99000, 101000)`, `ext3_harness` (stream prices stay within 99,550 to 100,450) |
| `lb_pool` | secondary | Liquibook, raw pointers into slots preallocated before timing (no heap allocation for order objects in the window); the style of Liquibook's own `test/perf/pt_order_book.cpp`, which builds all orders before timing |
| `map_unity` | secondary | repo engine, `std::map` book, compiled into the harness TU (`ext3_harness_unity`) |
| `lb_shared` | secondary | Liquibook, `OrderBook<std::shared_ptr<LbOrder>>` with `make_shared` per order, the style of Liquibook's `examples/mt_order_entry` |

No DepthOrderBook, BBO or depth listener is attached to Liquibook (its "Order Book Only" mode, its
fastest documented configuration); no trade listener; one order listener as described above.

Schedule (`run_timed.sh`): 5 rounds; each round runs the six configs in the fixed order
`map, lb_new, flat, lb_pool, map_unity, lb_shared`, one fresh process each (so primary runs
alternate A B ... A B within the interleaved sequence). 30 runs in total, 1,000,000 measured events
and 20,000 warm-up events each. Nothing else is run by this agent while the sequence runs.

### Load rule (added at the coordinator's request, before the freeze)

Other agents' jobs share this machine. The 1-minute load average (`sysctl -n vm.loadavg`, second
field) is recorded before every run.

1. Gate: the sequence starts only when the 1-minute load is below 3.0 (the audit's low-load runs
   were at 2.2 to 2.3). Poll every 60 s for up to 45 minutes.
2. If the gate passes: before each run, wait (poll every 15 s, at most 5 minutes) for load < 3.0,
   then run regardless; a run whose pre-run load is >= 3.0 is flagged `LOADED`.
3. If the gate fails after 45 minutes: run the full sequence anyway with no per-run waits; every
   run and every number is labelled **LOADED MACHINE** with its measured load, in RESULTS.md and in
   the report.

Interleaving spreads any drift in load across configurations; it does not remove load effects.

## 8. Outputs, summary and decision rule

Outputs in `benchmarks/ext3/results/<run_dir>/`: one `<config>_run<r>_summary.csv` per run,
`runs.csv` (one row per run with its load), `raw_stdout.txt` (machine, commits, stream hash, gate
polls, every run's stdout), and `summary.md` written by `summarize.py` (run with `python3 -I`).

Reported per config: median and min to max of events/s, p50 and p99 (and the load range).

Decision rule (fixed now): for a pair (X, Y), on events/s, **X is faster** if median(X) > median(Y)
and min(X) > max(Y) (the 5-run ranges do not overlap); symmetric for Y; otherwise **no clear
difference**. For p50 and p99, X is lower if median(X) < median(Y) and max(X) < min(Y). The primary
decision is `map` vs `lb_new` on events/s. All other pairs and the latency comparisons are secondary
and descriptive (same rule, labelled secondary). Ratios of medians are reported with the ranges and
are not called "X times faster" unless the primary rule says faster. If the sequence ran as
LOADED MACHINE, the decision is still computed and reported, labelled LOADED MACHINE, and is not a
clean-machine result.

All headline numbers stay "NOT YET REPLICATED" until an independent rerun from this file and an
adversarial fairness review are done.

```
cd benchmarks/ext3
./build.sh                                   # fetches Liquibook at the pinned commit, builds 3 binaries
./build/gen_stream build/stream_seed42.csv   # SHA-256 must equal the value in section 3
./build/ext3_harness check build/stream_seed42.csv          # must print EQUIVALENCE=PASS
./build/ext3_harness_unity check build/stream_seed42.csv    # must print EQUIVALENCE=PASS
./run_timed.sh results/<run_dir>
python3 -I summarize.py results/<run_dir>/runs.csv
```
